# Ресурсный бюджет

[values.yaml](../deploy/chart/values.yaml) содержит начальные лимиты, а не измерения
всего стека на вашей VM. Сумма memory limits постоянных контейнеров —
**6048 MiB (около 5.9 GiB)**. Остальная память нужна Ubuntu/k3s и кратковременным Job.
CPU requests позволяют разместить стек на 4 vCPU; сумма CPU limits может быть выше,
так как компоненты не нагружены одновременно.

| Компонент | Memory limit |
|---|---:|
| Airflow scheduler + локальная задача | 1280 MiB |
| Airflow API / DAG processor | 640 / 384 MiB |
| Metabase | 1024 MiB, JVM heap до 384 MiB, Metaspace до 384 MiB |
| Kafka | 896 MiB, JVM heap до 384 MiB |
| PostgreSQL main / DWH | 384 / 384 MiB |
| Garage | 256 MiB |
| Consumer | 192 MiB |
| Prometheus | 384 MiB |
| Четыре exporter | 224 MiB суммарно |

Airflow выполняет одну задачу одновременно; нет Celery/Redis, triggerer,
KubernetesExecutor или нескольких реплик. Deployment используют Recreate, чтобы
не удваивать RAM при rollout; краткий перерыв при обновлении допустим для лаборатории.

PVC запрашивают **37 GiB**: PostgreSQL 5 + 10, Garage 10, Kafka 4, Prometheus 3,
Airflow logs 2, дампы 3. Остальное — ОС, образы, containerd logs и запас.
**local-path не обеспечивает жёсткую дисковую квоту PVC**: следите за диском VM.

- Garage: квота бакета 8 GB / 100 000 объектов, очистка raw старше 30 дней.
- Kafka: 48 часов, 512 MiB на partition, сегменты 64 MiB. Служебные топики требуют
  дополнительного места; retention сегментов не является мгновенным жёстким пределом.
- Prometheus: 3 дня или 2 GB, плюс WAL и служебные файлы.
- Airflow: task logs 7 дней, метаданные запусков 30 дней.
- Дедупликация: 90 дней; ODS-матчи сохраняются.
- Дампы: несколько последних дней; Kubernetes/containerd logs ротируются.

Проверьте RAM, рестарты и диск после первой недели. Увеличивайте параллелизм только
после измерений. Образы рекомендуется собирать в GitHub, не на рабочей VM.


## Измерения

`python3 scripts/measure.py --scenario idle --seconds 60 --output /tmp/idle.json`
сохраняет потребление узла отдельно от Pod проекта. Повторите во время load,
backfill, backup и restart; сценарий задаёт метку, а не запускает нагрузку.
Не уменьшайте requests/limits на основании единственного снимка.

### Замер существующего стенда, 27 сентября 2026

Четыре выборки за 30 секунд: Pod проекта **2095–2102 MiB**, узел целиком
**6495–6533 MiB**, CPU узла **365–474m**. На диске оставалось 29 GiB.
Это прежние образы до обновления 0.3; на VM работают и другие приложения.
Замер выполнен вскоре после включения VM, поэтому не характеризует стабильную
нагрузку за день. Metabase потреблял около 844 MiB из лимита 1024 MiB.

Короткие замеры версии 0.3 приведены ниже. Лимиты не уменьшены,
публикация событий оставлена последовательной.
Снимки собирайте в отдельные JSON-файлы; не публикуйте kubeconfig и Secret вместе с ними.

### Версия 0.3 после обновления

Выборки каждые 10 секунд, 30–60 секунд на сценарий, 27 сентября 2026.

| Сценарий | Pod проекта, MiB | Весь узел, MiB | CPU узла, m |
|---|---:|---:|---:|
| idle | 2165–2176 | 6398–6448 | 263–372 |
| load | 1337–2174 | 5653–6482 | 1083–1449 |
| backfill | 1294–2186 | 5769–6476 | 302–1423 |
| backup | 2169–2183 | 6382–6470 | 360–1035 |
| restart | 505–1679 | 5429–6295 | 1379–3615 |

`load` — replay 18 матчей через настоящий DAG; `backfill` — один API-запрос
за 2026-09-08–2026-09-11; `backup` — три небольших дампа; `restart` — rollout,
не перезагрузка VM. Во время части измерений запускалась Metabase, работали
другие приложения и проверки. Метрики усреднены, поэтому краткие пики могли
не попасть в выборку. Это не стресс-тест и не доказательство запаса под большие
объёмы. Сравнение режимов публикации здесь не проводилось; оптимизация batching
отложена до измерений на большем наборе.
